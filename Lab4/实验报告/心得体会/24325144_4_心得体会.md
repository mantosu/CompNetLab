## 心得体会

这次排错让我第一次分清了 `transmit failed` 和 `Request timed out` 的区别。`Request timed out` 通常是包已经发出去了，但在路上被丢了，或者对方没有回；而 `transmit failed` 更像是本机在发送阶段就失败了，问题大概率在 PC 自己身上，比如没有默认网关、路由表冲突、多网卡选错出口，或者被防火墙拦截。当时 PC1 能 ping 通 `192.168.1.1`，说明 PC1 到 R1 的链路、IP、ARP 和二层通信都正常；`192.168.2.1` 又是 R1 的直连接口地址，R1 自己就有到 `192.168.2.0/24` 的直连路由，所以这个 ping 其实不依赖 OSPF 有没有学到路由。想明白这一点后，我才没有继续在 OSPF 配置里打转，而是回头检查 PC1 自己的路由和网卡状态。

这也让我重新理解了 OSPF 在拓扑里到底解决什么问题。它主要解决的是 R1 和 R2 互相学习对端非直连网段，比如 PC1 去 ping PC2；至于 PC 到本网段网关、到路由器直连接口能不能通，靠的是主机自己的地址、网关和直连路由。以前一遇到 ping 不通就容易怀疑路由协议，现在我会先按"主机 → 直连 → 路由 → 协议"的顺序排一遍，先确认基础项，再看 OSPF。

对 DR/BDR 的理解也比看书时具体了。R1、R2 在 `192.168.2.0/24` 上默认优先级都是 1，Router ID 大的更容易成为 DR；未手工配置 Router ID 时，设备通常选本地活动接口中最高的 IP，本次 R2 自动选到的 Router ID 是 `172.16.6.204`，按规则比较后 R2 更可能成为 DR、R1 成为 BDR，单路由器网段则自己就是 DR。DR/BDR 选举还有非抢占性，已有 DR/BDR 时，新加入的路由器不会立刻抢走角色；拔线或重启接口后观察重新选举，比只看书上的规则直观得多。

总的来说，网络"通不通"不是绝对的，同样的配置换一个目的地址、换一个回程方向，结果就可能不一样。协议配置正确只是其中一环，主机选路、双网卡、防火墙这些"协议之外"的因素同样会决定结果。排查时先弄清现象属于哪一类，再按顺序逐段确认，比一上来就改配置有效得多；结论也要以设备和主机的实际输出为准，不能只靠"上次能通"来推断。
